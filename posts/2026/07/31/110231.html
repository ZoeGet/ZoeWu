Codex无法使用GPT-5.6：CC Switch上游协议配置错误解决办法

Created2026-07-31|Updated2026-07-31|Codex
|Post Views:

问题现象

在 CC Switch 中配置第三方 API 中转后，Codex 可以正常显示供应商和模型，但 GPT-5.6 系列模型始终无法使用。

常见表现包括：

  • gpt-5.6-sol、gpt-5.6-terra、gpt-5.6-luna 全部调用失败；
  • 请求返回 404 Not Found、400 Bad Request 或模型不可用；
  • 旧模型可能还能使用，切换到 GPT-5.6 后立即报错；
  • API Key、余额、Base URL 和模型名称反复检查都没有发现问题；
  • 在其他聊天客户端中可以调用同一个 API，只有 Codex 不能使用。

这次问题的最终原因并不是 GPT-5.6 模型本身，也不是 Codex 没有模型权限，而是 CC Switch 中该供应商的上游协议配置错误：

将上游协议从 Chat Completions 改为 Responses 后，GPT-5.6 系列模型恢复正常。

最快解决办法

在 CC Switch 中执行下面的操作：

  1. 切换到 Codex 应用；
  2. 找到当前正在使用的 API 供应商；
  3. 点击编辑，展开高级选项；
  4. 找到“上游格式”或“上游协议”；
  5. 将 Chat Completions（需开启路由） 改为 Responses（原生）；
  6. 保存配置并重新启用该供应商；
  7. 完全退出 Codex，然后重新启动；
  8. 新建任务测试 gpt-5.6-sol。

如果配置的是已存在的供应商，升级 CC Switch 后也要手动检查一次。CC Switch v3.19.0 虽然已经把新建供应商的默认模型更新为 gpt-5.6-sol，但发布说明明确表示：已经创建的供应商会保留原来的配置，不会自动修正旧的上游协议。

根本原因：Codex和上游说的不是同一种协议

OpenAI 当前主要有两种文本生成 API：

协议 请求端点 主要请求字段
Chat Completions /v1/chat/completions messages
Responses API /v1/responses input、Items、Responses 工具结构

两种协议虽然都能完成文本生成，但请求路径、请求体、流式事件、工具调用和多轮状态结构并不相同，不能只修改 URL 就直接互换。

如果上游本来就提供原生 /v1/responses，CC Switch 却被配置成 Chat Completions，请求就可能被错误地发送到 /v1/chat/completions，或者进入不必要的协议转换流程。上游模型、工具调用或流式响应只要不兼容这种转换，就会出现 400、404、流式中断或模型不可用。

这也解释了为什么在普通聊天客户端中 API 可以使用，而在 Codex 中不行：普通聊天客户端可能直接发送 Chat Completions 请求，Codex 发送的却是 Responses 请求。

为什么GPT-5.6更容易暴露这个问题

这并不表示 GPT-5.6 在所有场景下都完全不能使用 Chat Completions。OpenAI 的 GPT-5.6 Sol 模型页同时列出了 /v1/chat/completions 和 /v1/responses 两个端点。真正的问题是：Codex 客户端与 CC Switch 上游之间的协议链路必须匹配。

GPT-5.6 的推理、工具调用、多轮状态和代理式工作流更适合 Responses API。OpenAI 也建议在推理、工具调用和多轮工作流中使用 Responses API。

如果中间层强行把 Codex 的 Responses 请求转换为 Chat Completions，除了端点不匹配，还可能遇到以下转换差异：

  • Responses 的 input 与 Chat Completions 的 messages 结构不同；
  • Responses 的工具类型不一定都能映射到 Chat Completions；
  • function_call_output、工具调用 ID 和开发者消息可能转换失败；
  • SSE 流式事件格式不同；
  • previous_response_id、持久化推理和上下文压缩可能需要额外适配；
  • 新模型支持的推理档位、图片输入和工具能力可能被旧的模型目录或转换模板限制。

只要上游原生支持 Responses，优先使用 Responses（原生） 可以减少一层转换，也更接近 Codex 的原生工作方式。

Responses和Chat Completions应该怎么选

不要看到这篇文章后，把所有供应商都无条件改成 Responses。正确选择取决于上游实际支持的协议。

上游情况 CC Switch上游格式 是否需要本地路由
上游原生支持 /v1/responses Responses（原生） 通常不需要协议转换
上游只支持 /v1/chat/completions Chat Completions 需要开启“本地路由映射”并保持代理运行
上游同时支持两种协议，主要用于 Codex 优先 Responses（原生） 通常不需要
上游模型为 DeepSeek、Kimi、GLM 等 Chat 格式模型 Chat Completions 需要 CC Switch 做 Responses ↔ Chat 转换
上游使用非标准完整路径 按真实协议选择 可能还要开启“完整 URL 模式”

CC Switch 从 v3.16.0 开始加入了 Codex 的 Chat Completions 路由能力：它可以把 Codex 发出的 Responses 请求转换成上游 Chat Completions，再把 JSON、SSE、推理内容和工具调用转换回 Responses。

但是这个功能有两个前提：

  1. 供应商的上游格式确实应当选择 Chat Completions；
  2. “需要本地路由映射”和 Codex 接管必须正确开启，而且 CC Switch 本地代理需要一直运行。

如果上游本身就支持 Responses，则没有必要绕到 Chat Completions 再转回来。

一个容易混淆的配置点

CC Switch 中的“上游格式”和 Codex config.toml 中的 wire_api 不是同一个概念。

  • wire_api = "responses" 表示 Codex 向供应商发送 Responses 请求；
  • CC Switch 的“上游格式”决定它收到 Responses 请求以后，是原样转发，还是转换成 Chat Completions；
  • 即使上游只支持 Chat Completions，Codex 侧的 wire_api 仍然是 responses，协议转换由 CC Switch 完成；
  • 不要尝试把 Codex 的 wire_api 改成 chat 或 chat_completions，这些不是当前支持值。

判断方法：

  • /responses 返回 404，但 /chat/completions 成功：选择 Chat Completions，并开启本地路由；

  • 两个端点都返回模型不存在：检查模型 ID、模型映射或账号是否有该模型权限；
  • URL 中出现 /v1/v1/、/v4/v1/：Base URL 被重复拼接，需要修正地址或使用完整 URL 模式。

常见报错与排查方向

报错或现象 更可能的原因 排查方法
404 /v1/responses 上游只有 Chat Completions，或 Base URL 错误 测试两个端点，确认上游格式
404 /v1/chat/completions 上游只提供 Responses，或错误选择了 Chat 改为 Responses（原生）
This model is only supported in v1/responses 请求被错误发送到 Chat Completions 检查 CC Switch 上游格式和中转站路由
400 且提示 messages、input 字段错误 请求体协议不匹配 检查是否发生了错误转换
invalid tool_call_id 工具调用在协议转换中丢失或错配 优先走原生 Responses，或升级 CC Switch
普通对话正常，工具调用或压缩失败 转换桥只覆盖了部分请求路径 检查路由日志和 CC Switch 已知问题
401 或 403 鉴权失败 检查 API Key、请求头和供应商权限
429 额度或速率限制 检查余额、并发限制和供应商状态
Model not found 模型名、映射、账号权限或中转站路由错误 先请求 /models，再核对真实模型 ID

建议的完整排查顺序

以后遇到 Codex 模型全部不可用，可以按照下面的顺序排查：

  1. 确认 CC Switch 当前启用的是正确供应商；
  2. 检查 Base URL 是否多写或少写了 /v1；
  3. 查询 /models，确认真实模型 ID；
  4. 分别测试 /responses 和 /chat/completions；
  5. 根据测试结果选择 CC Switch 的上游格式；
  6. 如果选择 Chat Completions，确认“需要本地路由映射”和 Codex 接管已经开启；
  7. 检查 config.toml 中 wire_api = "responses"；
  8. 保存后完全退出并重启 Codex；
  9. 查看 CC Switch 路由日志中的真实请求 URL、状态码和上游错误；
  10. 最后再排查 API Key、余额、模型权限和供应商故障。

截至 2026 年 7 月 31 日，CC Switch 最新发布版为 v3.19.0。该版本已经将新建供应商的 GPT 默认模型更新为 gpt-5.6-sol。如果使用较旧版本，建议先升级，再重新保存供应商配置后测试。

本次问题的最终结论

这次故障的核心不是“Codex 不支持 GPT-5.6”，而是：

最终修复方式是：

修改后保存配置，重启 Codex，GPT-5.6 系列模型即可恢复使用。

需要特别记住的是：

  • Codex 侧始终使用 Responses 线协议；
  • 上游原生支持 Responses 时，CC Switch 应选择 Responses（原生）；
  • 上游只有 Chat Completions 时，才选择 Chat，并开启 CC Switch 本地路由转换；
  • “能显示模型”不代表“协议配置正确”，模型列表、端点协议和账号权限需要分别验证。
